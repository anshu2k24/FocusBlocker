1. Executive Summary & Problem Statement

Modern mobile operating systems provide constant notifications and high-dopamine triggers from social media platforms (such as Instagram and Facebook) and hyper-engaging video games. For students and working professionals, this leads to fragmentation of focus, reduced study throughput, and chronic procrastination.

FocusBlocker is an autonomous, native Android application engineered to enforce distraction-free focus intervals. It enables users to select specific distracting apps or games and designate a scheduled focus start time. When the scheduled focus hour arrives, the application actively monitors device usage in the background and intercepts restricted apps in real time by displaying an unskippable full-screen barrier. To allow flexibility for urgent communications or brief relaxation, the system incorporates an integrated temporary revoke (pause) protocol allowing access for 5, 10, 15, or up to 30 minutes, after which enforcement automatically resumes.

Key Engineering Principles
  • No Root Required: Operates entirely through sanctioned, modern Android framework APIs (UsageStatsManager and AppOpsManager).
  • Zero Battery Bloat: Utilizes a lean 1-second scheduled task, screen-state gating via PowerManager.isInteractive(), and minimal memory overhead.
  • Crash-Resilient & Sticky: Registered as an Android 14 compliant Foreground Service with type specialUse and automatically survives device reboots via a static BOOT_COMPLETED BroadcastReceiver.

3. Detailed Source Code Walkthrough

3.1 Persistence Abstraction: PrefsHelper.java

All persistent state is stored in Android's private internal storage under /data/data/com.example.focusblocker/shared_prefs/focus_blocker_prefs.xml. PrefsHelper encapsulates all CRUD operations to provide thread-safe, defensive data access.

Defensive Copying in SharedPreferences

When retrieving a Set<String> from SharedPreferences via getStringSet(), Android returns an internal reference. Directly modifying that set leads to silent data corruption. PrefsHelper.getBlockedPackages() guarantees safety by creating an independent clone: return new HashSet<>(set);. 

// Dynamic default to current system clock:
public static int getStartHour(Context context) {
    Calendar now = Calendar.getInstance();
    return getPrefs(context).getInt(KEY_START_HOUR, now.get(Calendar.HOUR_OF_DAY));
}

public static int getStartMinute(Context context) {
    Calendar now = Calendar.getInstance();
    return getPrefs(context).getInt(KEY_START_MINUTE, now.get(Calendar.MINUTE));
}

public static void setStartTime(Context context, int hour, int minute) {
    getPrefs(context).edit()
            .putInt(KEY_START_HOUR, hour)
            .putInt(KEY_START_MINUTE, minute)
            .apply();
}

3.2 Application Controller: MainActivity.java

MainActivity serves as the primary configuration dashboard. It handles three distinct responsibilities:

  1. Dynamic Permission Auditing: Checks both Usage Access (via AppOpsManager) and System Alert Window (via Settings.canDrawOverlays). Crucially, this audit is performed inside onResume(), ensuring that whenever a user returns from Android Settings, the status badges update to "Granted" immediately.
  2. 12-Hour AM/PM TimePicker with Real-Time Listener: Configured with timePickerStart.setIs24HourView(false) to prevent military 24-hour confusion. An attached OnTimeChangedListener immediately writes any adjustment to PrefsHelper, allowing the running background service to register time adjustments without stopping or restarting.
  3. Live Countdown Timer: Employs a UI Handler running every second to calculate remaining temporary revoke minutes and update the status card dynamically (Waiting vs Active). 
// Real-time synchronization whenever the user spins the TimePicker:
timePickerStart.setOnTimeChangedListener((view, hourOfDay, minuteOfHour) -> {
    PrefsHelper.setStartTime(MainActivity.this, hourOfDay, minuteOfHour);
    updateScheduleStatusDisplay();
});

3.3 App Discovery & Category Filtering: AppSelectActivity.java

This activity scans the device for user-launchable applications using PackageManager.queryIntentActivities().

  • Background Thread Execution: Loading application metadata and icon drawables for 100+ apps takes time. To keep the UI silky-smooth, the querying is offloaded to Executors.newSingleThreadExecutor() and posted back to the main thread via Looper.getMainLooper().
  • Automated Game Categorization: Uses ApplicationInfo.category == ApplicationInfo.CATEGORY_GAME and FLAG_IS_GAME. The "Select All Games" button iterates through the model list, marks all games as checked, and updates the UI instantly.
  • Pre-Selection Logic: On initial run, if Instagram (com.instagram.android) or Facebook (com.facebook.katana) are installed, they are checked by default.

3.4 Core Monitoring Engine: BlockService.java

BlockService is the architectural heart of FocusBlocker. It runs as a persistent Foreground Service with a 1-second background poll.

Solving the Continuous In-App Usage Challenge

In Android, UsageStatsManager.queryEvents() only logs an ACTIVITY_RESUMED event when a window transitions from paused to resumed. If a user is already browsing Instagram for 5 minutes, zero new resume events are emitted during those 5 minutes!

A naive query of the last 10 seconds would return null, meaning the app would fail to block unless the user closed and reopened Instagram. FocusBlocker solves this by retaining the active foreground identity across ticks in currentForegroundApp. When the clock strikes the block start time, currentForegroundApp immediately triggers BlockActivity over the screen right in the middle of active scrolling! 

// Continuous Foreground App Tracking Implementation:
private String getForegroundPackageName() {
    UsageStatsManager usageStatsManager = (UsageStatsManager) getSystemService(Context.USAGE_STATS_SERVICE);
    if (usageStatsManager == null) return currentForegroundApp;

    long endTime = System.currentTimeMillis();
    long startTime = endTime - 15000; // Query recent window

    UsageEvents events = usageStatsManager.queryEvents(startTime, endTime);
    if (events != null) {
        UsageEvents.Event event = new UsageEvents.Event();
        while (events.hasNextEvent()) {
            events.getNextEvent(event);
            if (event.getEventType() == UsageEvents.Event.ACTIVITY_RESUMED) {
                currentForegroundApp = event.getPackageName(); // Update state on transition
            }
        }
    }

    // Historical fallback for initial service startup:
    if (currentForegroundApp == null) {
        UsageEvents history = usageStatsManager.queryEvents(endTime - (2 * 3600 * 1000L), endTime);
        if (history != null) {
            UsageEvents.Event event = new UsageEvents.Event();
            while (history.hasNextEvent()) {
                history.getNextEvent(event);
                if (event.getEventType() == UsageEvents.Event.ACTIVITY_RESUMED) {
                    currentForegroundApp = event.getPackageName();
                }
            }
        }
    }
    return currentForegroundApp;
}

3.5 Blocking Screen & Bypass Interceptor: BlockActivity.java

When launched, BlockActivity occupies the entire screen. It incorporates critical viva-worthy mechanisms:

  • Back-Navigation Interception: Back presses are captured via getOnBackPressedDispatcher().addCallback() and routed to Intent.CATEGORY_HOME, ensuring the user cannot bypass the block using gesture navigation or the Back button.
  • "Go Home" Button: Triggers an explicit Intent to the Android home screen launcher and finishes the activity.
  • Temporary Revoke Protocol: Offers 5, 10, 15, or 30 minutes in a Material Spinner. Upon confirmation, it writes revokeUntil = System.currentTimeMillis() + (minutes * 60 * 1000) into SharedPreferences and finishes, unblocking the app until the pause period elapses.
// Back press override to ensure unskippable enforcement:
getOnBackPressedDispatcher().addCallback(this, new OnBackPressedCallback(true) {
    @Override
    public void handleOnBackPressed() {
        Intent homeIntent = new Intent(Intent.ACTION_MAIN);
        homeIntent.addCategory(Intent.CATEGORY_HOME);
        homeIntent.setFlags(Intent.FLAG_ACTIVITY_NEW_TASK);
        startActivity(homeIntent);
        finish();
    }
});

3.6 Device Reboot Interceptor: BootReceiver.java

To ensure user discipline cannot be defeated by turning the device off and on, BootReceiver listens for android.intent.action.BOOT_COMPLETED. 

public class BootReceiver extends BroadcastReceiver {
    @Override
    public void onReceive(Context context, Intent intent) {
        if (Intent.ACTION_BOOT_COMPLETED.equals(intent.getAction())) {
            if (PrefsHelper.isBlockingEnabled(context)) {
                Intent serviceIntent = new Intent(context, BlockService.class);
                ContextCompat.startForegroundService(context, serviceIntent);
            }
        }
    }
}

4. Oral Examination (Viva) Preparation Guide

Viva Question 1: What is the difference between a Started Service and a Bound Service?

Answer: A Started Service is initiated via startService() or startForegroundService() and runs indefinitely in the background until it completes its task or is explicitly stopped via stopService(). A Bound Service offers a client-server interface initiated via bindService(), which lives only as long as an active client is bound to it. FocusBlocker uses a Started Foreground Service.

Viva Question 2: Why do we pass FLAG_ACTIVITY_NEW_TASK when launching BlockActivity from BlockService?

Answer: In Android, activities belong to task back-stacks. Services do not possess an activity back-stack. When launching an activity from a non-activity context (such as a Service or BroadcastReceiver), Android throws a RuntimeException unless FLAG_ACTIVITY_NEW_TASK is supplied to instruct the Window Manager to create or assign a new task.

Viva Question 3: Why is AppOpsManager used instead of standard checkSelfPermission for Usage Stats?

Answer: PACKAGE_USAGE_STATS is a privileged system permission that cannot be granted at runtime through the standard permissions dialog. It is governed by Android's AppOps subsystem. Thus, AppOpsManager.unsafeCheckOpNoThrow() must be used to query whether the user has toggled the permission in Settings.

Viva Question 4: How does FocusBlocker avoid draining the battery?

Answer: FocusBlocker avoids battery drain by: (1) Running on a low-frequency 1-second interval without CPU wake-locks, (2) Reading PowerManager.isInteractive() to halt event queries when the phone screen is off, and (3) Using lightweight in-memory comparison rather than repeated disk or network I/O.

Viva Question 5: Why did we need android:foregroundServiceType="specialUse" for Android 14?

Answer: Starting in Android 14 (API 34), Google introduced strict categories for Foreground Services (e.g. camera, microphone, dataSync). Apps that perform app-restriction or focus-monitoring must use specialUse and document their purpose in both the manifest property PROPERTY_SPECIAL_USE_FGS_SUBTYPE and developer console to prevent service termination.

5. Command-Line Build & Installation Reference

Compile Debug APK:

cd ~/FocusBlocker
./gradlew assembleDebug

The compiled artifact is generated at: app/build/outputs/apk/debug/app-debug.apk

Install to Connected Phone:

adb devices
adb install -r app/build/outputs/apk/debug/app-debug.apk

Initial Phone Setup Checklist:

  1. Usage Access: Open FocusBlocker → Tap Grant → Toggle "Allow usage tracking".
  2. Display Over Other Apps: Tap Grant → Toggle "Allow display over other apps".
  3. Notifications: Tap Grant to allow persistent monitoring notifications (Android 13+).
  4. Battery Optimization: Phone Settings → Apps → FocusBlocker → Battery → Choose Unrestricted.
